自动检查与行动授权各管什么

设计一个有明确退出条件的检查流程，识别检查不能决定的事项。

建议 22 分钟 · 案例为虚构练习，不是实际业务数据。

事件触发解决的是时机问题

Claude Code 的 hooks 可在特定事件发生时触发处理逻辑。它们适合执行重复、可明确判定的动作，比如记录检查结果或发现缺少某个必要字段。事件触发本身不能证明检查规则正确，也不保证所有操作都被覆盖。设计前要说明事件、检查对象、通过条件和失败输出，并用当前官方文档核实支持方式。本课只练习规则设计，不提供可直接应用的配置或执行脚本。

通过检查不等于获得授权

结果检查回答“是否符合已定义条件”，权限机制回答“是否允许执行某个动作”。文件格式通过检查，不能据此推断可以发邮件、删除资料或发布线上修改。某些 hook 事件能影响权限流程，这属于额外的权限策略设计，不能由一个内容检查随意代替。规划自动流程时，把读取、生成草稿、保存、发送等动作分别列明，按照用户已给的授权和环境实际权限执行。

重试要有止损和可解释出口

发现错误后自动要求修正，可能形成“检查失败、重新修改、再次失败”的循环。给重试安排次数或时间上限，并区分可修复的内容错误、缺少外部输入和检查器自身故障。失败输出应说明哪项条件未满足以及证据位置，不要只说“不合格”。达到上限后保存现状并报告阻塞，而不是放宽标准以获得通过。最初可先手动运行相同检查，确认它确实能够发现预设错误。

Worked example / 原创案例

独立虚构案例：展览说明稿的字段检查

海窗馆每张展品说明必须有名称、年代和资料出处。某张说明没有年代，准备流程只授权生成草稿。

可尝试的任务说明

请设计说明稿检查规则，用自然语言描述即可。缺名称或出处视为内容未完成；年代没有资料时允许写“待考证”，但不得编造。最多检查两轮，仍有问题就列出缺项和所需资料。即使检查通过，也只返回草稿和记录，不发送给印厂。

怎么看结果

  1. 检查关注字段和证据，年代未知被显式展示，避免自动修复把空白变成虚构事实。
  2. 两轮上限防止循环；发送印厂属于另外的动作授权。规则通过后，还需要人核对资料能否支持年代描述。
Your turn / 动手练习

为一种重复文档设计自动检查，但先在纸面上模拟。

  1. 写三项可以明确判定的条件和一项需要人判断的条件。
  2. 准备合格、缺字段和资料未知三种输入，模拟检查输出。
  3. 列清流程中的动作授权，并写出重试上限、失败记录和退出后的处理。

验收清单

  • 每项自动条件都有明确通过和失败例子。
  • 未知资料不会被自动补成确定事实。
  • 流程明确写出检查通过后允许的动作，以及仍需另行决定的动作。

完成状态仅保存在当前浏览器；不代表工具或平台认证。

容易踩的坑

  • “多做几轮直到完成”没有退出条件，容易让成本和错误同时扩大。
  • 自动检查规则若只检测字段存在，仍无法证明字段内容真实。
