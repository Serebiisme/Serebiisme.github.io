Claude Code for Product Work / 04

把 PRD 写成团队能作决定的文档

从问题与证据出发，补齐规则、异常路径和验收。

建议 50 分钟 · 案例为虚构练习，不是实际业务数据。

先确定问题和边界

一份 PRD 的价值在于减少实施中的猜测。开头交代用户在什么任务上失败、证据是什么、为何现在值得解决。再明确本次范围和暂缓内容。让 Claude 先列出缺少的信息，而不是用熟悉的功能模板填满文档；未知项需要负责人和下一步。

目标应连接用户行为。例如“让用户能在开课前找到取消入口”可以通过任务测试观察，“提升体验”无法直接验收。业务指标可以另列，但不要把界面可用性与长期业务效果混成一个承诺。

功能要覆盖状态变化

写规则时从初始状态走到结束状态：没有预约、有预约、已过截止时间、网络失败、重复操作。每个状态说明用户看到什么、能做什么、系统保存什么。发现冲突时给团队一个明确选项，例如“超过截止时间只能联系值班人员”，并标记它需要谁确认。

验收采用可重现情景

把“支持取消”改成可执行检查：给定一笔尚未开始的预约，点击取消并确认后，该预约显示已取消，再次打开仍保持该状态。把失败也写进验收：请求失败时保留原预约并允许重试。评审重点不是文档长短，而是工程、设计和运营能否据此得出一致行为。

Worked example / 原创案例

虚构案例：图书交换柜提醒

读者到柜前才发现取书期限已过。团队拟做提醒，但短信预算和逾期规则尚未确定。

可尝试的任务说明

依据这份虚构问题记录起草一页 PRD。目标是减少因忘记期限导致的无效到访。先列出未知项；首版仅考虑站内提醒。写出提醒触发、已领取后停止提醒、失败重试的规则，以及五个可人工执行的验收情景。未经证据支持的预期收益请标为假设。

怎么看结果

  1. 将短信排除出首版，避免让未确认预算变成实现依赖。
  2. 区分“期限前提醒”与“逾期后说明”，后者涉及运营规则，暂列待决定。
  3. 用已领取、临近期限和提醒失败三个场景评审规则，发现重复提醒问题并增加停止条件。
Your turn / 动手练习

为一个小功能写不超过两页的 PRD。

  1. 选一个具体用户失败，附上两条虚构证据。
  2. 补齐正常流程和三个异常状态。
  3. 让另一位读者只凭文档执行验收，记录解释不一致处。

验收清单

  • 每项未知决定都有负责人或下一步。
  • 至少三个异常情景有明确用户反馈。
  • 验收能说明输入、操作与预期结果。

完成状态仅保存在当前浏览器；不代表工具或平台认证。

容易踩的坑

  • 让模型自行填写收益百分比，会制造没有来源的商业承诺。
  • 把所有审查意见直接加进范围，会让首版失去明确的任务。
