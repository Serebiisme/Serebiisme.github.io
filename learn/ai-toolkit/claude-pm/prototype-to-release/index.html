Claude Code for Product Work / 08

把原型、Git 和发布连成可检查交付

用最小原型验证任务，并在公开发布前明确版本和影响。

建议 55 分钟 · 案例为虚构练习，不是实际业务数据。

原型先验证一个任务

先定义用户要从哪里到哪里。例如“找到可借雨伞并选择取伞时段”，首版就围绕这条路径。用虚构数据，说明哪些行为只是演示。Claude Code 可以帮助创建和修改原型，但你需要检查界面反馈与状态变化，不能只看首页截图。

把需求改成有限页面和状态：列表、详情、确认、无库存、提交失败。先让工具解释实现范围，再开始制作。若原型要接入真实账户或支付，它已经涉及更大的行为范围，需要重新确定数据与发布要求。

版本是一次有理由的变化

Git 记录文件变化，提交保存快照，分支容纳不同方向；GitHub 是托管与协作平台。一次修改围绕一个可解释目标，保留修改理由和检查结果。评审文件差异比凭印象判断可靠。已有别人未完成的改动时先识别归属，避免混入本次交付。

发布是另一项决定

本地运行、预览地址和正式公开地址是不同阶段。发布前确认访问范围、演示数据、页面链接、手机可用性，以及怎样撤回。最终交付记录版本、地址和已知限制。访问一个页面成功只证明它能打开；完整验证还要走过用户任务，检查刷新后的状态与失败提示。

Worked example / 原创案例

虚构案例：借伞试用原型

你想给三名试用者演示预约，尚未决定是否公开，也没有真实库存接口。

可尝试的任务说明

请制作虚构借伞原型，使用本地演示数据，包含选伞、选时段、确认和无库存状态。界面注明演示，确认页不能表示真实预约成功。先给范围与检查清单，再制作并提供本地预览。完成后说明文件变化和限制，不发布到公开网站。

怎么看结果

  1. 用一个伞点和两个时段完成主路径，避免把演示扩成完整运营系统。
  2. 检查无库存时不能提交，确认页显示演示预约；手机上逐项操作。
  3. 记录可评审版本。若后续获准发布，按该版本生成预览，确认公开资料和撤回方法，再检查线上相同路径。
Your turn / 动手练习

用纸面页面或本地原型演练一次小交付。

  1. 选一个三步以内的用户任务并列出失败状态。
  2. 修改一次界面，记录原因与前后行为。
  3. 写一份交付说明，分清可运行、已检查与待发布。

验收清单

  • 完成说明没有把模拟操作写成真实交易。
  • 至少检查一条正常路径和两条失败路径。
  • 发布范围与恢复办法在公开操作前已明确。

完成状态仅保存在当前浏览器；不代表工具或平台认证。

容易踩的坑

  • 提交不等于上传，上传代码也不等于网站部署成功。
  • 图片和凭据可能随公开仓库或网站暴露，发布前应检查实际文件。
