Claude Code for Product Work / 03

把分工和记忆写成可维护约定

让代理独立处理明确任务，并让长期背景保持准确。

建议 40 分钟 · 案例为虚构练习，不是实际业务数据。

按信息边界拆任务

子代理适合独立的侧任务：不同访谈的提取、不同方案的审查，或大量背景资料的筛选。Claude Code 的子代理有独立上下文和可配置工具权限。分工时提供它实际需要的输入，不要假定它知道主对话里的所有决定。

拆分的关键是输出能否合并。要求每个代理使用相同的证据编号、字段和不确定性标记。若甲负责改需求、乙同时改相同文件，合并会变成第二项任务。让他们分别返回审查意见，由一个负责人决定修改，通常更容易控制。

审查角色必须有问题

“扮演资深专家”容易得到宽泛建议。把角色变成检查任务：运营审查容量和人工兜底，研究审查证据是否支持结论，工程审查状态与失败路径。不同角色都来自同一个模型时，意见相同也不等于多位独立专家已经确认。你仍需回到证据和实际约束。

长期记忆只存稳定背景

CLAUDE.md 可提供项目说明；自动记忆可以记录学习到的偏好。它们是上下文，不是强制权限。把目标用户、术语、资料位置与审查规则写短，把本周临时目标放在任务简报。每条容易变化的约定标记更新日期与负责人；过期背景比缺少背景更容易误导下一次工作。

Worked example / 原创案例

虚构案例：校园失物招领

你准备评审“失物领取预约”需求，希望发现运营和隐私方面的问题。

可尝试的任务说明

请分别从运营执行和资料最小化两方面审查这份虚构需求。每份意见列出具体条目、问题依据、严重程度与建议，先不要改原文。合并时保留分歧；最后给我一份需要人工决定的清单。

怎么看结果

  1. 运营审查发现预约时段超过值班人数，资料审查发现不必要的证件字段。
  2. 主任务将两项问题映射到需求段落，比较修改是否会改变领取流程。
  3. 把“领取时人工核验，预约不收证件照片”作为待批准决定。批准后的规则才进入项目说明，未决定事项留在简报中。
Your turn / 动手练习

对同一份小需求做两种独立审查，并写一份项目约定。

  1. 给两个角色不同的检查问题与统一返回格式。
  2. 整理冲突意见，写下采用或拒绝的依据。
  3. 从本次任务中挑出三条长期规则，移除临时日期与未经确认结论。

验收清单

  • 两份审查意见都定位到需求的具体条目。
  • 合并记录至少解释一个取舍。
  • 项目约定不包含账户秘密或本周一次性任务。

完成状态仅保存在当前浏览器；不代表工具或平台认证。

容易踩的坑

  • 代理数量增加会增加上下文与协调成本，小任务不必拆开。
  • 把“绝不修改某文件”写入记忆，并不替代实际工具权限控制。
