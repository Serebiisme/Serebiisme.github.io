Codex for Product Delivery / 07

把 Git 与上线验证变成交付记录

形成包含版本、构建、访问地址和限制的可追踪发布交接。

建议 45 分钟 · 案例为虚构练习，不是实际业务数据。

先检查即将保存什么

版本保存前查看工作区状态和改动差异，确认本次修改文件、生成文件和别人的未提交内容。只把本次工作纳入版本，不用“全部添加”掩盖不明文件。提交说明写用户可观察的改变及原因，验证记录写实际执行结果。远程推送或发布前明确目标仓库、分支和可见范围，使用已有授权；练习阶段可以先把这些信息整理成待执行清单。

静态托管有能力边界

GitHub Pages 官方将它定义为从仓库提供 HTML、CSS 与 JavaScript 的静态网站托管。前端演示可以发布，服务端代码不会因文件上传而变成运行中的 API。密钥不能放入公开前端文件；需要后台能力时另行选择适合的服务。读取项目现有构建说明再决定部署方法，不猜包管理器或构建命令，也不承诺所有托管方案都适合当前项目。

上线完成以访问结果为准

发布后核对构建状态、目标提交和公开地址，再用新浏览器会话检查首页、直接进入子路径和静态资源。测试刷新、窄屏以及核心操作，尤其注意本地可用而线上路径错误的情况。交接记录写明提交编号、发布时间、访问结果、已知限制和回退方式。仅收到构建成功还不足以证明用户能访问，地址可打开也不足以证明关键流程有效。

回退方案要指向实际可用的旧版本，并说明如何重新验证。不要只写“有问题就撤回”；维护者需要知道撤回后页面会变成哪个版本、模拟数据是否受影响，以及用哪条用户路径确认恢复。

Worked example / 原创案例

发布星港的只读器材演示

虚构网站没有真实预约服务，团队决定把合成器材目录作为静态演示公开。

可尝试的任务说明

先只读检查仓库和当前改动，列出发布目标、构建方式、拟纳入文件和线上验收。依据已有明确发布授权执行；若缺目标信息，先给完整交接草稿。公开页面写明演示数据。

怎么看结果

  1. 检查差异排除私有访谈和无关修改，确认目录页面都为合成数据。
  2. 核对发布对应的提交，再从线上直接打开器材详情子路径。
  3. 记录核心页面、资源加载与刷新结果，并说明预约只是模拟交互。
Your turn / 动手练习

为一个静态原型写发布交接，可先在本地完成预发布检查。

  1. 检查本次文件与敏感资料。
  2. 列出构建、目标、版本与验收。
  3. 记录访问结果或明确未发布状态。

验收清单

  • 记录能对应到唯一版本。
  • 公开范围与内容清单清晰。
  • 未发布或未验证事项没有被写成已完成。

完成状态仅保存在当前浏览器；不代表工具或平台认证。

容易踩的坑

  • 构建成功不等于线上行为通过。
  • 公开仓库与私有仓库的托管可用性需查当前设置。
